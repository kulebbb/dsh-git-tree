dsh-git-tree · 更新入口方案 · 2026-11-18

让用户主动查更新，一点直达更新按钮

这篇回答两件事：Git 提交图面板怎么让用户自己发现新版本，以及点下去之后怎么用最少的步骤完成更新。结论是学 dsh-context-optimize 的分工——面板只负责「发现 + 领路」，换包与回滚交给 DSH 插件页；但比它多一个手动检查入口，并修掉现在会误导人的「假提示」。文末有三件事需要你拍板，确认前我不动代码。

方案 · 已按方向 A 实施（0.7.3） DSH 0.2.2-rc.3 本机安装方式未改 本机是 GitHub 安装，当前无法应用内更新 本地仓库落后 origin/main 4 个提交

一、先给结论

要做的是三件小事，不是重写更新模块：

  • 主动发现：状态条右侧常驻一个版本胶囊（如 v0.7.0），点开是更新浮层，里面永远有一个「检查更新」动作；不再只靠启动时偷偷查一次。
  • 快捷更新：查到新版本时，浮层里点「去更新」，直接打开 DSH 插件页里本插件的详情页——那一页的「版本」区已经带着「更新到 0.7.2」按钮。插件自己不下载、不装包、不改 profile。
  • 修掉假提示：现在只要 npm 上有更高版本就亮横幅，哪怕本机是从 GitHub 装的、插件页根本没有更新按钮。新逻辑先看安装来源，只有「npm 同名安装」才把用户往更新按钮上领。

先说人话 · 为什么不能「点一下就在面板里装好」

插件是跑在 DSH 里的客人，不能一边跑着一边把自己脚下的地板换掉。换包、失败回滚、热更新，这些都必须由 DSH 这个「房东」来做。所以面板能做的是把「有新版本」这件事摆到你面前，并把你送到房东的操作台前——剩下的那一下，由插件页完成。这也是 dsh-context-optimize 的选择。

二、参考对象到底做了什么

dsh-context-optimize 的做法可以拆成三段：我们只有最左边那段的「被动提示」，缺的是其中的「用户可主动触发」和「点击后领路」；中间和右边本来就归 DSH，不用我们重写。

它的显示规则尤其值得照抄——目标不是「有新版就喊」，而是「喊了以后一定有更新按钮可点」：

判定规则防的是什么
安装来源只认 profile 里以版本号 / 范围安装的同名 npm 包；link:、file:、Git、裸 URL 不进入「可更新」状态点了跳到插件页却发现没有「版本」区
版本资格只认正式版，且该版本清单里声明了 dsh.bundle把用户引到一个装不上的版本
版本高低比当前版本高才提示；相等或更低不提示反向赞歌与重复打扰
失败网络、超时、坏 JSON 全部静默降级面板里多一个「检查失败」添噪
版本资格 · 为什么不能直接把 npm 的「最新版」拿来用

npm 上的最新版本不一定能装进 DSH：它可能是个测试版，也可能压根没声明自己是 DSH 插件。插件页在列版本时会先筛一遍，我们如果只看「最新版号」，就会出现「我们点亮了、插件页却没有更新按钮」的死路。所以判定要和插件页的主要标准一致：正式版、声明了 dsh.bundle、未被弃用；engines.dsh 与 peer 兼容由插件页最后把关。

三、现状的三个问题

假提示

现在的检查只看 npm registry 最新版，不看本机是怎么装的。本机是 github:kulebbb/dsh-git-tree，DSH 对这种未锁定提交的 Git 安装不提供更新按钮——横幅却照样会亮。

只查一次

检查只在插件启动时跑一次，结果存在内存里。启动时断网、或者 DSH 开了很久，就再也不会重新查；用户也没有任何「现在查一下」的入口。

入口是被动横幅

横幅只有一行灰字「请在插件页重装以更新」，不能点、不能跳转，也不会告诉你去插件页的哪一页。用户看完还是得自己找。

第三点还带来一个隐性体验问题：横幅出现时占一行、可以关掉，关掉后本次面板实例内不再出现；而「当前版本是多少」这个排查问题时最常被问到的信息，面板里根本没有。

这不是假设：本机安装的是 10 月 29 日从 GitHub 拉的 0.7.0，直接请求正在运行的面板接口，返回是 {"current":"0.7.0","latest":"0.7.2","newer":true}——横幅现在就会亮。可插件页面对这个 Git 安装没有更新按钮，点过去只能重装。假提示是当下正在发生的事，不是将来的风险。

四、方案总览

保留现有只读接口的形态，扩成一条「带缓存、可手动刷新」的版本状态接口；客户端在状态条加一个版本胶囊，点开是更新浮层。整条链路四步：

宿主半：从「启动查一次」变成「按需查、可刷新」

同一个 GET /git-tree/update/status 路由：首次请求才查，成功缓存 1 小时、失败缓存 5 分钟，并发请求共享同一次网络调用；加 ?refresh=1 跳过读缓存（仍写缓存并更新检查时间），供「检查更新」按钮使用。认证沿用 0.7.2 起的 ctx.connection.admit()，不新开免认证路径。安装来源从宿主注入的 profileContext.dir 读 profile 的 package.json 判定。

客户端半：胶囊 + 浮层，删掉旧横幅

状态条右侧加 v0.7.0 胶囊；点击弹出浮层，按安装来源与检查结果给不同文案和主操作。有新版时胶囊变成 ↑ v0.7.2 并染色，这是唯一主动提醒。旧的一行文字横幅删除，避免两套提示并存。

为什么胶囊常驻 · 不是有更新才出现

「用户主动发现」的前提是先有一个稳定的入口。胶囊平时就是个版本号，点开能查；有新版时它自己变成蓝色并带上新版本号。这样既不会在没更新时打扰你，也不会出现「面板里根本找不到检查更新在哪」的情况。

可识别性单独说明：真实状态条里还有「本地」「云端」两个哈希胶囊（原型已补上），加一个约 56px 的入口会先挤它们。所以做了两层处理：胶囊用 24px 高、带描边和 title/aria-label「检查更新（当前 v0.7.0）」，一望可知是可点的；宽度小于约 460px 时收成 24px 的 ↑ 图标，入口不消失，版本号改在浮层里显示。代价是窄栏时哈希胶囊会更早出现省略号，这是需要接受的取舍。

点「去更新」之后落在哪

不是我们自己画的页面，而是 DSH 插件页里本包的详情页。版本区一打开就会自动查一次，通常直接能看到「更新到 0.7.2」：

插件 › 已安装
@kulebbb/dsh-git-tree 可更新
版本 0.7.2 · 正式版
更新期间插件会短暂停止；安装失败会保留或重新安装 0.7.0。
落点是 DSH 自己的页面，我们不重画、不代点

拿不到 pluginNavigation 服务时（老 DSH 或权限受限），浮层里的「去更新」退化为在浏览器新标签打开 npm 页面，和 dsh-context-optimize 的兜底一致。

首帧与失败态也要定义：还没拿到状态时胶囊显示 v—，浮层写「尚未检查」，点一下就查；检查中按钮禁用并显示「正在检查…」，避免连点。交互按原生控件做：胶囊带 aria-haspopup / aria-expanded / title；Esc 先关浮层（搜索框打开时先关搜索，二者不同时存在），焦点还给胶囊；浮层里的按钮都是原生 <button>，Tab 顺序自然，不设焦点陷阱。

六、方向对照

推荐：方向 A · 版本胶囊 + 浮层

常驻入口最稳，各种状态都有地方安放；默认不打扰，有新版才染色。代价是多一个浮层组件的交互与无障碍细节（Esc、点外关闭、焦点回胶囊），以及窄栏时要在「胶囊」和「图标」两种形态间切换。

方向 B · 横幅 + 状态条检查图标

更醒目，但没更新时入口只剩一个没有文字的箭头；有更新时横幅又永久占一行。等于用两处入口换一次醒目，窄侧栏尤其挤。

方向 B 的实际样子，两种状态放在一起看：没更新时横幅不出现，只剩状态条上一个 ↑ 图标；有更新时横幅占掉一行。

七、判定规则与接口

和 dsh-context-optimize 共用主要的判定口径，但把「不提示」改成「提示并说明原因」——入口常驻，不会把用户带进死路。每个状态底部都保留「检查更新」。

情况浮层显示主操作
npm 安装 + 有更高正式版新版本 vX去更新（跳插件页）
npm 安装 + 已是最新已是最新版本仅「检查更新」
Git 安装 + 锁定 40 位提交Git 安装（已锁定提交）打开插件页（更新在「发现」页）
Git 安装 + 未锁定提交Git 安装，不支持快捷更新打开插件页 / 打开 npm
本地目录安装（link: / file:）本地目录安装打开插件页
网络失败 / 超时 / 坏 JSON检查更新失败 + 原因检查更新（重试）
读不到 profile 或安装来源未知无法判断安装方式检查更新 / 打开 npm
老 DSH 没有 pluginNavigation仍显示新版本打开 npm 页兜底

接口仍是 GET /git-tree/update/status，载荷扩成：

{ ok, current, latest, newer, installSource, canUpdate, checkedAt, checkError }

newer 保持原义（registry 版本更高），不破坏现有契约；新增 installSource（registry | git | local | unknown）、canUpdate（只有 registry 安装且 newer 才为 true）、checkedAt（上次检查时间戳）。?refresh=1 跳过读缓存但仍写缓存。非 GET 仍返回 405；认证沿用现有 admitRequest，未认证请求仍是 401/403。

安装来源判定读 profile 的 package.json（dependencies / devDependencies / optionalDependencies 三处都看），和 dsh-context-optimize 的实现一致；读不到时按 unknown 处理，只有手动检查能给出「无法判断安装方式」的说明，不会误报可更新。

版本资格只做能低成本核实的部分：dist-tags.latest、正式版、声明 dsh.bundle、未被 deprecated。与当前 DSH 的 engines.dsh / peer 兼容性交给插件页最终把关——本包 0.7.2 这两项都为空，等以后声明了再补，属于已知残留风险。

和参考实现有一处不同：Git / 本地目录安装也会查一次 npm（只在你点开浮层时告诉你「有新版本，但当前装法不支持应用内更新」），但胶囊不会染色、不主动打扰。原因是你现在就是 GitHub 安装，完全不查等于连「该换 npm 了」都没人提醒。

九、实施步骤

  1. 先同步基线：本地 checkout 落后 origin/main 4 个提交（0.7.0 → 0.7.2，含宿主认证与工作区限制）。先快进到 origin/main 再动手；这算一次合并，需要你点头。
  2. 宿主判定先行：重写 lib/update.js 的版本解析与来源判定，先把「什么情况下算可更新」用单测钉死，再改路由。
  3. 路由改成按需 + 可刷新：状态对象带 TTL 与并发去重；refresh=1 强制重查；无 profileContext 时安全降级。
  4. 客户端胶囊与浮层：先做纯函数（状态到文案/动作），再接入面板；跳转用 ctx.get('pluginNavigation')?.openBundle(name)，失败退回 npm 页。
  5. 删旧横幅与清理：去掉 showUpdateBanner 与相关文案，防止两套提示并存。
  6. 测试与文档：node --test 全绿；补决策记录；README 的「新版本提示」章节改写。
  7. 验证分两层：单测覆盖判定、缓存与状态机；真实面板先验证「本机 GitHub 安装」这条分支（胶囊、检查更新、打开插件页）。npm 一键更新分支要同时满足「registry 安装 + 有新版本」，预发布前走不通：可以临时把新 lib 覆盖到已从 npm 安装的 profile 副本、并把版本降到 0.7.1 来演示（需要你许可改 profile，且不点最终确认）；或者等发布 0.7.3 后再发 0.7.4 做真实验证（生产操作，另行批准）。
最后一步为什么绕不开 · 安装来源决定按钮存不存在

Git 安装也分两种：锁定到 40 位提交的，更新入口在插件页的「发现」标签页；用分支 / 标签装的，插件页连「版本」区都没有。本机是后者（github:kulebbb/dsh-git-tree 没锁提交），所以完整的一键更新链路要先换成 npm 安装才走得通——这是一次性的手动动作，不是代码能绕过的。

十、风险与不做的事

项处理
老 DSH 没有 pluginNavigation不硬依赖：拿不到就新标签打开 npm 页；胶囊照常显示
registry 在国内不可达第一源 npmjs、第二源 npmmirror；两个都失败才显示「检查失败」
浮层被状态条裁切和现有 tooltip 一样用 fixed 定位，按视口边缘收拢；状态条不改 overflow
反复点「检查更新」打爆 registry刷新也写缓存（只跳过读）；并发共享同一请求；客户端再加 10 秒最小间隔
GitHub 安装用户看到「不支持更新」以为是故障文案明确写「重新安装 npm 版本后即可一键更新」，并给 npm 链接
新增参数削弱认证refresh 只影响缓存，路由仍先过 connection.admit()；不新增免认证路径
窄侧栏（< 360px）挤爆状态条胶囊 flex:none + 省略号；窄时只保留版本号，不隐藏检查入口；现有 pill 的收缩行为不变
浮层被 tooltip 或面板容器盖住沿用 tooltip 的 fixed 定位，z-index 取 1002（比 tooltip 高 1）；不塞进 overflow:hidden 的状态条

明确不做：面板内自绘更新进度、失败回滚、忽略此版本、轮询、侧边栏红点。前两项 DSH 插件页已经做得更稳，后三项会让插件和平台两套状态打架。

十一、需要你拍板

1. 快捷更新的落点：跳插件页，还是面板里真装？

推荐跳插件页：和 dsh-context-optimize 一致，零安装风险，DSH 负责换包与回滚。若你坚持在面板里装，需要调用 pluginManager.updateBundle 并自绘进度与失败三态，约三百行，且第三方插件自更新时请求可能因包被卸载而中断——我不推荐。

2. 本机安装来源：要不要从 GitHub 换成 npm？

不换的话，新功能能看到、能查、但「去更新」落到插件页没有更新按钮，只能重装。换成 npm 后这条链路才完整。这一步会改桌面 profile（~/.dsh/profiles/desktop），需要你明确许可，我只在你同意后做。

3. 视觉方向：A（胶囊 + 浮层）还是 B（横幅）？

推荐 A。确认方向后我再开始改代码；如果 A 的某处文案或交互你想调整，直接说，我改原型再实施。
