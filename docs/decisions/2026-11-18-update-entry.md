# 决策：面板只负责「发现更新 + 领路」，换包交给 DSH

- 日期：2026-11-18
- 状态：代码已实施，待发布 0.7.3
- 影响版本：0.7.3 起
- 相关：`lib/update.js`、`lib/index.js`、`lib/client.js`、`test/update.test.js`、`test/update-ui.test.js`、`README.md`、`docs/api.md`

## 背景

0.7.0 起，插件只在启动时静默查一次 npm，然后在面板里显示一条只读横幅：「新版本 x（当前 y），请在插件页重装」。这条提示有两个问题：

1. 不看安装来源。只要 npm 上有更高版本就亮，哪怕本机是 `github:kulebbb/dsh-git-tree`（未锁定提交）或 `link:` 安装——这两类安装都没有「版本」区，用户点不到任何更新按钮。
2. 没有主动入口。启动时离线、或者 DSH 开了很久，就再也不会查；用户也无法要求「现在查一下」。

## 决定

1. 宿主改成**按需检查**：`GET /git-tree/update/status` 首次被请求时才查 registry；成功缓存 1 小时、失败缓存 5 分钟；`?refresh=1` 跳过读缓存（仍写缓存）。
2. 新增安装来源判定：读 `profileContext.dir` 下的 `package.json`，把依赖值分成 `registry | git | local | unknown`；只有 `registry` 且满足「更高、正式版、声明了 `dsh.bundle`、未被弃用」时 `canUpdate` 才为 `true`。
3. 客户端在状态条加常驻版本入口（窄栏收成 24px 图标），点开是更新浮层；浮层在任何状态都保留「检查更新」。有可更新版本时点「去更新」调用 `pluginNavigation.openBundle()`，落到 DSH 插件页本包详情；没有该服务时打开 npm 页。
4. Git / 本地目录安装不再染色，只说明原因并给「打开插件页 / 打开 npm」出口。
5. 删除旧的只读横幅与 `showUpdateBanner` 导出。

## 为什么

- **权限边界**：插件跑在自己的代码里，换包、失败回滚、热更新必须由 DSH 插件管理器做。第三方插件自己执行 pnpm 会与 App 抢 profile 锁，0.7.0 已经因此删过一次。
- **不制造死路**：DSH 插件页只给「npm 同名安装」和「锁定到 40 位提交的 Git 安装」提供更新入口。只看 npm 最新版就提示，等于把用户送到一个没有按钮的页面。
- **常驻入口才叫主动发现**：版本号本身也是排查问题时要问的信息；把入口放在状态条，平时不打扰，点开就能查。

## 影响与注意事项

- 发布 0.7.3 后，npm 安装的用户会看到「↑ v0.7.4」并可一键跳转更新；GitHub（未锁定提交）与 `link:` 安装看不到可更新，只会看到说明。
- 本机当前是 GitHub 安装，所以这份代码上线后仍不能在本机完成一键更新；要验证完整链路，需发布后切到 npm 安装。
- 仍然没有安装/更新写接口：`/git-tree/update/status` 是只读 GET。
- 手动刷新失败时保留上一次成功结果并标 `stale`，避免一次网络抖动把更新入口抹掉。
- `gist:`、自建 Git host（锁提交）归为 Git；tarball 归为 unknown，不制造假的「去更新」。
- `newer` 字段保留原义，新增 `installSource`、`canUpdate`、`checkedAt`；`docs/api.md` 已同步。

## 未验证

- 真实环境里的「去更新 → 插件页版本区 → 更新到 x」链路需要「registry 安装 + 有更高版本」同时成立；发布前无法在本机完整走通。
- 更新后是否需要重启由 DSH 的实际结果决定：面板文案写「能热更新就直接生效，否则按提示重启」，没有承诺必定免重启。
- `engines.dsh` / peer 兼容性没有在插件侧比对，交给插件页最终把关；本包 0.7.2 这两项都为空。
